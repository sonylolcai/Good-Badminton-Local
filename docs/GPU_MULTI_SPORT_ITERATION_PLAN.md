# GPU 双运动独立部署迭代方案

状态：固定运动入口、模式同步、独立发布包和 WebUI 路由已实现；固定入口同时提供整视频任务与分片流接口。
范围：GPU 视觉分析与配套 WebUI 适配
不在范围：自动计分、胜负、排名、业务报告、能量估算、人工身份认领规则

## 1. 已确认的产品与部署约束

1. 羽毛球业务和网球业务长期独立运行，可以使用不同业务服务器、GPU 服务器和 WebUI。
2. 一台 GPU 服务器只部署一种运动，不支持在同一运行实例中切换或混跑两种运动。
3. 两种运动共用视频处理、人体姿态、匿名追踪、任务状态和事件传输能力，避免重复维护。
4. 场地几何、运动员观察范围、球模型、球轨迹参数和模型版本由各自运动实现维护。
5. GPU 输出匿名视觉事实：人物框、COCO17 姿态、`track_id`、人物位置、球位置、置信度、缺失状态、质量和运行追踪。
6. 现有羽毛球能力在迁移过程中保持可用；网球能力通过新入口逐步加入。
7. 实现遵循当前项目的本地约定，并对关键状态、兼容逻辑和失败策略保留详细注释。
8. 网球第一阶段只支持两种视觉会话模式：`singles_match`（单打比赛）和 `single_player_training`（单人训练），不支持双打。
9. `singles_match` 固定追踪 2 名运动员；`single_player_training` 固定追踪 1 名近端运动员，可以只拍摄和标定近端半场。
10. 训练模式中的发球机不是人物 roster 成员，GPU 不负责识别发球机、推断发球规则或生成训练结论。

## 2. 目标结构

同一个代码仓库保留三个部分：共享视觉核心、羽毛球适配、网球适配。运行时入口在进程启动时注入唯一的运动适配，业务请求不能改变该运动。

```text
vision_core/
  streaming/             视频分片、顺序、采样、checkpoint、事件持久化
  detection/             通用人体姿态调用及模型缓存
  tracking/              匿名人物关联、track_id、质量、短缺失状态
  geometry/              四角透视变换和坐标系统
  contracts/             通用人物/球观测结构

sports/
  badminton/
    profile.py            羽毛球场地和视觉参数
    ball_detector.py      羽毛球模型适配
    ball_tracker.py       羽毛球候选筛选和短轨迹处理
  tennis/
    profile.py            网球场地和视觉参数
    ball_detector.py      网球模型适配
    ball_tracker.py       网球候选筛选和短轨迹处理

apps/
  badminton_gpu/app.py    羽毛球 GPU 唯一启动入口
  tennis_gpu/app.py       网球 GPU 唯一启动入口

webui/
  shared/                 上传、状态、标定交互、任务历史、观测结果
  apps/badminton.py       羽毛球分析 WebUI 入口
  apps/tennis.py          网球分析 WebUI 入口
```

这是目标结构，不要求第一步移动全部文件。迁移期保留 `api.app`、`badminton_analysis.*` 和现有契约作为兼容入口，内部逐项转到新模块。

## 3. 共享核心的职责

共享核心只接收运行入口注入的实现，不包含 `if sport == ...` 分支。

### 3.1 保留在共享核心

- 视频、完整文件和 1–2 秒分片的解码。
- `analysis_session_id`、`segment_index`、SHA-256、幂等接收和严格顺序处理。
- 人物检测、COCO17 姿态、ByteTrack 关联和匿名 `track_id`。
- 由运动与会话模式注入的 roster 人数约束；共享追踪实现必须支持 1、2、4 人，但不能自行决定某种运动允许哪些人数。
- `detected`、`predicted`、`missing`、`candidate` 等证据状态。
- 模型缓存、采样调度、取消、性能追踪和 checkpoint 外壳。
- 四角透视变换的数学实现。
- 通用 `person_observation`、`ball_observation`、`session_status` 事件。
- 候选人物照片裁剪。该能力保持可选，GPU 不做身份识别。

### 3.2 从共享核心排除

- 自动计分、胜负、排名、挑战和比赛结果。
- 羽毛球高远、吊、杀等球路结论，以及网球正反手、截击等动作结论。
- 回合规则、发球规则、界内外结论和报告文案。
- 身高体重、能量估算和能力分数。

### 3.3 视觉参数与业务规则的界线

运动入口可以配置视觉算法必须知道的事实：会话模式、场地尺寸、网的位置、人物观察多边形、球搜索区域、roster 人数、模型路径、采样率和筛选阈值。

计分规则、落点是否得分、回合归属等信息继续由各自业务端维护。GPU 可以在未来输出有证据的触球或反弹候选，但它们仍是候选视觉事件，不是比赛结论。

### 3.4 三条链路的固定边界

```text
业务服务：保存场馆/比赛/规则并解释匿名视觉事件
    │ 只发送 opaque client_reference、分片顺序、标定和 visual session_mode
    ▼
模式同步：api/mode_sync.py
    │ 固定入口的 profile 推导人数、几何和人物观察范围；拒绝换运动或冲突人数
    ▼
视觉解析：api/stream_runtime.py + shared tracker/pose/geometry
    │ 只产生匿名人物、姿态、位置、球候选、质量和运行追踪
    ▼
GPU HTTP：apps/<sport>_gpu/app.py + api/app.py
```

固定运动入口通过 `api.app.create_app(profile)` 同时暴露 `/api/v1/jobs` 和分片流接口，但不包含业务判分、报告或大模型教练逻辑。`api.gpu_stream_app` 继续保留为只需要分片观测时的裁剪入口。

## 4. 运动适配接口

每个入口提供一个固定的 `SportVisionProfile`，建议至少包含：

```text
sport_id
service_name
supported_session_modes
session_mode_profiles
coordinate_system_id
court_dimensions_m
court_line_reference
calibration_scope
calibration_world_points_m
athlete_observation_region_policy
ball_observation_region_policy
expected_roster_count
min_roster_count
max_roster_count
person_sample_hz
ball_processing_mode
pose_model
ball_model
ball_detector_factory
ball_tracker_factory
model_manifest
```

`court_dimensions_m` 只负责建立标准场地坐标。人物观察范围必须独立配置，因为网球运动员会站到底线外；球搜索范围也不能限制为地面场地四边形。

网球 profile 内提供两个固定模式：

| `session_mode` | roster | 标定范围 | 人物观察范围 | 球观察范围 |
|---|---:|---|---|---|
| `singles_match` | 2 | 完整单打场地 | 两端单打运动区域及底线后合理外扩 | 完整画面内的有效来球区域 |
| `single_player_training` | 1 | 完整场地或近端半场 | 仅近端运动员训练区域 | 独立配置，可覆盖发球机来球进入画面的路径 |

训练模式不能用“人物观察区域”裁剪球候选。发球机、教练或远端路人落在人物区域之外时不进入 roster；球即使从人物区域之外进入画面，仍应由独立球观察区域处理。

半场标定时，四个图像点对应“近端单打半场”的四个已知世界坐标点，例如近端球网线两角和近端底线两角。共享透视变换必须接收显式的 `calibration_world_points_m`，不能把所有四点都硬解释为完整场地外角。输出事件必须携带 `calibration_scope` 和 `coordinate_system_id`，避免业务端把半场坐标误解为整场标定结果。

羽毛球适配先封装当前模型和阈值，保持现有结果。网球适配使用独立模型、训练数据和筛选参数。两者可以实现同一个球观测接口，但不能共享未经验证的运动模型阈值。

## 5. GPU 接口迭代

### 5.1 保持羽毛球 v1 兼容

- 当前 `stream-session.v1` 请求和 `shuttle_observation` 在迁移期继续可用。
- `api.app:app` 暂时映射到羽毛球入口。
- 旧任务、历史事件和 checkpoint 继续可读；不在原文件上改写历史结果。

### 5.2 增加通用 v2 观测契约

建议新增 `sport-vision-session.v2`，包含：

- `sport_id`：业务请求必须与服务器固定运动一致，不一致返回明确错误。
- `session_mode`：网球仅接受 `singles_match` 或 `single_player_training`；羽毛球继续使用自己的模式集合。
- `expected_player_count`：由服务器固定的运动与会话模式推导，网球单打为 2、训练为 1；客户端不能提交与模式冲突的人数。
- `person_sample_hz`：人体与姿态采样频率。
- `ball_processing_mode`：球按采样帧处理或按连续源帧时序处理。
- `calibration`：标定范围、图像点、对应世界坐标点、人物观察范围、球观察范围及标定版本。
- `model_manifest`：人体、球、追踪模型的名称、版本和文件摘要。
- `person_observation`：人物框、姿态、位置、关联和质量。
- `ball_observation`：二维中心/框、置信度、检测来源和缺失状态。

人体和球不能继续共用一个固定的 `analysis_sample_hz`。网球球速与人物运动尺度不同，球处理是否需要每个源帧必须通过真实视频测试确定，而不是被人体 10/15Hz 的预算限制。

### 5.3 健康检查和防止误连接

每个 GPU 实例的健康接口返回：

```json
{
  "status": "ok",
  "sport_id": "tennis",
  "service_name": "good-tennis-gpu-api",
  "contract_versions": ["sport-vision-session.v2"],
  "build_sha": "...",
  "models": {
    "pose": "...",
    "ball": "...",
    "tracker": "..."
  }
}
```

业务端和 WebUI 在提交任务前校验 `sport_id`。错误连接时禁止提交，避免网球视频进入羽毛球模型。

## 6. WebUI 更新方案

### 6.1 运行方式

- 提供羽毛球 WebUI 和网球 WebUI 两个启动入口。
- 运动类型由入口或只读部署配置决定，页面不提供运动切换控件。
- 页面顶部持续显示当前运动、GPU 连接目标、服务端返回的运动、契约版本和模型版本。
- 页面配置与 GPU 返回的运动不一致时，分析按钮禁用并显示明确原因。

### 6.2 当前 Gradio 分析 WebUI

`webui/app.py` 逐步拆成共享页面结构和运动文案/配置。网球入口需要以下变化：

1. 品牌、标题和帮助文字改为网球。
2. 只提供“单打比赛”和“单人训练”模式，不出现双打选项；人数由模式固定为 2 或 1，不再让用户自由填写。
3. “羽毛球/球头/球路”等文案改为当前运动对应的“网球/球位置/轨迹”。
4. 球模型选择只展示网球服务器支持的选项，不暴露羽毛球权重路径。
5. 单打比赛使用完整单打场地标定，并预览两端运动员观察范围。
6. 单人训练允许选择“完整场地”或“近端半场”标定；选择半场后，页面明确引导点击近端球网线两角和近端底线两角，不能继续显示完整场地四角提示。
7. 人物观察范围与标定范围分开预览；训练模式只高亮近端运动员区域，并明确提示远端人员、教练和发球机不计入 roster。
8. 球观察范围独立预览，允许覆盖发球机来球进入画面的路径，不随近端人物区域一起裁剪。
9. 训练模式只展示近端 1 名运动员的人物框、骨架、匿名 ID、位置与质量；单打模式展示 2 名运动员。
10. 结果页保留球二维位置、轨迹、缺失状态、置信度和性能追踪。
11. 网球 GPU WebUI 不显示羽毛球球种、无球回合窗口、赛后身体数据、计分和比赛报告页签。
12. 任务历史记录显示固定 `sport_id`、`session_mode`、`calibration_scope`、服务实例、模型版本和构建版本。

第一版网球标定允许“自动选择清晰视频帧 + 人工四点确认”。当前自动球场线检测基于羽毛球线型，不能直接作为网球自动标定能力。网球自动线检测应作为后续独立迭代。训练视频若只显示近端半场，不得要求用户猜测画面外的远端场角。

### 6.3 `webui-next` GPU 运维页

`webui-next/src/app/gpu` 当前只管理一个基础地址和密钥。适配后增加：

- 页面部署身份：羽毛球运维版或网球运维版，由构建配置固定。
- GPU 状态字段：`sport_id`、`build_sha`、契约版本、模型版本。
- 保存配置时立即请求健康接口并校验运动类型。
- 运动类型不匹配时不保存为 ready，也不允许发起 start/stop 以外的分析操作。
- 显示当前活动任务、队列数量和最后一次运动匹配检查结果。
- 保持 API Key 不回显的现有行为。

`webui-next` 的场馆、球场和业务页面未来可由两个业务产品分别演进；本方案只要求 GPU 运维页理解固定运动实例。

## 7. 独立部署与打包

### 7.1 构建产物

建议生成两个独立包：

```text
good-badminton-gpu-api-<version>.zip
good-tennis-gpu-api-<version>.zip
```

每个包包含共享核心、一个运动适配、一个启动入口、对应依赖清单和部署清单。羽毛球包不得包含网球模型，网球包不得包含羽毛球模型和球处理实现。

### 7.2 部署身份

| 项目 | 羽毛球 | 网球 |
|---|---|---|
| 启动入口 | `apps.badminton_gpu.app:app` | `apps.tennis_gpu.app:app` |
| 进程名称 | `good-badminton-gpu-api` | `good-tennis-gpu-api` |
| 应用目录 | `/root/good-badminton-gpu-api` | `/root/good-tennis-gpu-api` |
| 状态目录 | `/root/good-badminton-gpu-api-state` | `/root/good-tennis-gpu-api-state` |
| 上传包名 | `good-badminton-gpu-api-upload.zip` | `good-tennis-gpu-api-upload.zip` |

共享部署实现可以放在 `deploy/common/`，由两个小型运动脚本提供固定目录、进程名称和包身份。部署清单必须写入 `sport_id`；更新脚本在停止旧进程前验证包的运动身份，拒绝错误包。

当前可复现的固定运动 GPU 启动命令如下。两个网球视觉会话模式是**同一个网球进程内的会话配置**，不应各启一个服务；这样业务端不能靠切换进程来改变视觉约束。

```bash
# 羽毛球：固定 apps.badminton_gpu.app:app
bash deploy/start_badminton_gpu_container.sh /root/good-badminton-gpu-api

# 网球：固定 apps.tennis_gpu.app:app；.gpu-api.env 中设 GOOD_SPORT_VISION_PROFILE=tennis
bash deploy/start_tennis_gpu_container.sh /root/good-tennis-gpu-api
```

旧命令 `start_gpu_api_container.sh` 仅向后兼容地转发至羽毛球固定入口。共享启动器只允许上述两个 entry point，拒绝可由环境变量任意指定模块。

### 7.3 发布包裁剪

GPU 生产包使用源码白名单，不再复制整个仓库。固定运动生产包不包含：

- `business_gateway/`
- 运动指标、报告和人工复核实现
- `webui-next/`
- 业务数据库迁移
- 原始视频、输出、训练集和未使用模型

若旧整文件入口仍需要 WebUI pipeline 和渲染依赖，将其作为羽毛球兼容包的可选能力，不进入网球纯观测试点包。

## 8. 迭代阶段

### R0：建立不可退化基线

交付：

- 固定当前羽毛球流式请求、事件、checkpoint 和结果样例。
- 标记当前整文件入口仍执行的击球/回合推导和位置图。
- 记录可用羽毛球样本的近端/远端人物覆盖、ID 中断、球覆盖和阶段耗时。

放行条件：现有流式测试、GPU 接口测试和契约测试通过；基线文件不含密钥或原始用户身份。

### R1：提取共享视觉核心

交付：

- 提取流式引擎、通用姿态、匿名人物追踪和纯坐标变换。
- 将人物观察范围从场地四角中分离。
- 移除纯流式链内部的 `person_id`、`team_id`、回合和业务统计状态。
- 旧导入路径使用兼容适配，保持羽毛球行为。

放行条件：

- 羽毛球观测字段、时间戳、证据状态和有效 `track_id` 行为不退化。
- 位于合法人物观察范围、但在底线/边线外的人物不再被场地四边形丢弃。
- ByteTrack 进程重启仍明确失败或要求回放，不伪造连续 ID。

### R2：建立两个固定运动入口

交付：

- `BadmintonVisionProfile` 和现有羽毛球入口。
- `TennisVisionProfile` 和网球入口骨架，固定声明单打比赛与单人训练两个模式。
- 将共享人物追踪器当前最少 2 人的约束改为 profile 注入；羽毛球仍只接受原有 2/4 人，网球单打只接受 2 人，网球训练只接受 1 人。
- 健康接口返回固定运动身份和模型清单。
- 请求运动与实例身份不一致时拒绝。

放行条件：两个入口分别启动；同一进程只注册一个 profile；羽毛球 v1 请求继续工作。

### R3：网球人物与 WebUI MVP

交付：

- 完整单打场地与近端半场两种标定映射，以及各自人物观察区域。
- 网球 WebUI 独立入口、品牌、模式选择、人工四点标定、人物与球区域独立预览。
- 网球视频的人物框、姿态、匿名 ID、二维地面位置和质量结果。
- Gradio 与 `webui-next` 的运动身份校验。

放行条件：

- 固定机位单打样本稳定保留 2 名运动员，底线后球员不被过滤，第三人不进入正式 roster。
- 单人训练样本在完整场地与近端半场画面中都能以 1 人完成 roster 锁定，不会等待第二名运动员。
- 训练模式只输出近端运动员；发球机、教练和远端路人不进入 roster。
- WebUI 不出现双打、羽毛球球种和业务分析控件；任务不能发送到错误运动实例或提交与模式冲突的人数。

### R4：网球球位置 MVP

交付：

- 网球检测模型适配和独立权重。
- 网球球候选筛选、连续轨迹状态和 `ball_observation`。
- 人体与球采用独立采样/处理节奏。
- 训练模式的球观察区域独立于近端人物观察区域，能够接收从发球机方向进入画面的球。
- WebUI 展示球的二维位置、轨迹、置信度、原始检测/预测/缺失状态。

放行条件：使用人工标注的完整视频计算清晰、模糊、遮挡和背景混淆场景的召回、误检、坐标误差和最长缺失；达到经基线评审确认的阈值后才能称为网球球位置可用。

### R5：独立发布包与真实 GPU 验收

交付：

- 两个源码白名单包、两个固定启动入口和两个更新脚本。
- 构建清单、文件摘要、运动身份和模型摘要。
- WebUI 到对应 GPU 的完整任务、事件和历史恢复流程。

放行条件：

- 从干净目录安装两个包，各自健康检查返回正确运动。
- 对错误包、错误服务地址和错误模型清单失败关闭。
- 羽毛球和网球分别完成至少一段真实固定机位流式测试。
- 真实长视频验收需记录分片接收、失败/积压、人物与球证据、最长缺失、ID 切换和阶段耗时；不能用本地单元测试替代。

## 9. 测试矩阵

| 测试层 | 共享核心 | 羽毛球 | 网球 |
|---|---|---|---|
| 单元测试 | 顺序、时间、checkpoint、匿名追踪、证据状态、1/2/4 人可配置 roster | 当前 2/4 人约束、模型适配和旧契约 | 单打 2 人、训练 1 人、近端人物过滤、球区域独立 |
| 契约测试 | v2 通用事件及禁止业务字段 | v1 兼容映射 | `sport_id=tennis`、两个合法模式、模式与人数冲突拒绝 |
| 集成测试 | 分片、取消、恢复、事件游标、profile/checkpoint 一致性 | 羽毛球入口与包 | 单打完整场、训练完整场/半场、错误模式恢复拒绝 |
| WebUI 测试 | 任务状态、错误展示、历史 | 羽毛球文案与控件 | 无双打、两种模式、半场提示、人物/球区域预览和错误实例阻断 |
| 视频评估 | 时间轴一致性 | 羽毛球基线不退化 | 单打 2 人、训练近端 1 人、球位置和长缺失指标 |

数据集必须按完整视频或完整比赛切分训练、验证和测试，不能将同一视频的相邻帧随机分到不同集合。

## 10. 完成定义

全部满足后，才认为 GPU 与 WebUI 的双运动独立部署完成：

1. 同一代码仓库维护共享核心，但羽毛球和网球有独立启动入口。
2. 任一服务器只能启动一种运动，健康接口能证明其身份。
3. 两个发布包只携带各自运动实现、模型清单和固定入口。
4. WebUI 没有运行时运动切换，且会阻止连接错误运动的 GPU。
5. 两种运动共用人物框、姿态、匿名追踪、时间、质量和事件结构。
6. 场地几何、人物观察区域、球搜索区域、球模型和筛选参数分别维护。
7. 纯 GPU 流式链不生成计分、结果、排名、能力报告和能量估算。
8. 羽毛球旧契约和现有可用流程经过兼容验证。
9. 网球人物与球位置经过真实固定机位视频评估，结果含覆盖率、误检、坐标误差、最长缺失、ID 切换和耗时。
10. 包结构、安装、启动、健康检查、任务提交、事件拉取和恢复均有可复现验收记录。
11. 网球只暴露单打比赛和单人训练；训练支持近端半场标定、只锁定近端 1 人，且球不受人物区域裁剪。

## 11. 当前事实与待验证事项

当前事实：

- 流式 GPU 入口已经以匿名人物/姿态和可选羽毛球观测为主。
- `stream-session.v1` 以 `person_only` 为视觉模式，并由固定入口校验 `sport_id` 与会话模式。
- 本分支已将 `expected_player_count=1` 与最小 1 人 roster 支持下沉到共享追踪；固定 sport/profile 会继续限制羽毛球为 2/4 人、网球单打为 2 人、网球训练为 1 人。
- 人物过滤已支持独立的边线和底线扩展；网球当前分别为 0.75 米和 3 米。
- 当前羽毛球和人物处理共用 `analysis_sample_hz`。
- 当前自动场地线检测与场地叠加是羽毛球专属实现。
- 发布和更新脚本已按羽毛球、网球固定目录、包名和入口校验部署身份。

待验证：

- 网球球检测选用的模型和权重。
- 网球视频所需的球处理帧率、分辨率与远端球尺寸。
- 单个网球 GPU 部署的吞吐、显存和最长任务时延。
- 单打模式两端人物观察范围、训练模式近端人物观察范围和球搜索范围的默认扩展比例。
- 训练视频常用机位下，近端半场四点的可见性与人工标定误差。
- 网球自动场地线检测是否值得进入第一版。
