# 单局两秒采集、连续分析与用户交付

## 目标

运营人员点击现有的“开始采集”时，场馆端创建一个新的对局 ID（复用现有 edge ingest session ID），开始每两秒产生、上传和持久化一个 MP4；GPU 立即按片段顺序分析。点击现有的“停止视频”时，终端停止产生片段并完成该对局。业务服务器将已经到达的连续片段封存为一条完整原始 MP4，并融合已经产生的 GPU 结构化结果，交付用户完整录像、分析成片和可选的解释性复盘。

不采集全天录像；不新增“开始对局/结束对局”按钮；开始/停止采集就是对局边界。

## PTS 的含义

PTS（presentation timestamp，展示时间戳）是“这一帧在本局录像开始后第几秒/毫秒出现”的标记。它不改变画面、不增加编码或传输成本。它只用于：将 GPU 的人物、轨迹和事件准确叠回完整录像；检查片段是否乱序/缺失；在片段边界融合证据。当前 `source_start_time_sec = segment_index * 2` 是一种相对时间线；本任务应让该时间线在整个对局 session 内明确、连续并随结果持久化。

## 当前可复用行为

- `deploy/venue-gateway/agent.py` 已在收到 `record` 控制后创建一次 session，持续产生两秒 H.264 MP4，停止时调用完整接口。
- `business_gateway/edge_api.py` 已保留分片，要求序号连续，并用 FFmpeg `-c copy` 封存 `recording.mp4`。
- GPU 的 `AnalysisEngine` 已支持顺序片段、检查点、恢复、乱序等待和重复幂等。

## 目标行为

1. 开始采集 = 创建本局 ID；停止视频 = 结束本局 ID。每片的序号、相对 PTS、哈希和 GPU 回执都归属到这一局。
2. GPU 分析每两秒片段，但同局片段按序进入同一可恢复会话。跟踪、轨迹和回合上下文跨片保存；必要时使用很小的边界重叠，不重复计入结果。
3. 停止后不把完整 20 分钟视频再送 GPU 重跑。服务器仅校验、封存完整原始录像，融合已存在的 PTS 结果；只有缺片、失败或低置信边界才创建局部补算。
4. 用户视频从完整原始 MP4 和统一 PTS 标注一次渲染；不得拼接各片的 GPU 视频输出。
5. 完整录像可供视觉模型/大语言模型进行异步复盘，但输入必须是 PTS 绑定的视频窗口、关键帧和已知 CV 事实；模型输出仅为解释或待核验建议，不能改写测量事实。

## 不在范围

- 全天持续采集、前后置缓冲、独立 `match_clip` 数据模型和新的开始/结束对局 UI。
- WebRTC 归档或作为 GPU 唯一输入。
- 对正常已分析完整对局进行第二次全片 GPU 分析。
- 具体 VLM/LLM 厂商接入、密钥或自动裁判结论。

## 接受标准

- `AC-01`：开始采集创建唯一对局 ID；停止后该 ID 的分片连续性和完整性可查询。
- `AC-02`：同一局的片段按序进入一个 GPU 会话，检查点恢复后跟踪/时间线不重置；重传不重复处理。
- `AC-03`：连续片段可无二次编码封存为完整原始 MP4；缺段明确为 `incomplete`，不伪装为完整。
- `AC-04`：最终对局统计和标注只融合实时片段已产生的 PTS 证据；正常完成不触发全片 GPU 重跑。
- `AC-05`：失败或低置信边界只产生明确的局部补算任务；源流实际缺帧只标记，不捏造。
- `AC-06`：VLM/LLM 的异步证据包和输出有 PTS 来源、用途和不确定性标记。
- `AC-07`：沿用现有“开始采集/停止视频”UI，补充本局完整性、最终交付和复盘状态，而非增加重复控制。
