# Good-Badminton Stream Session Contract v1

Status: **frozen for tasks A–F**
Contract version: `stream-session.v1`
Last updated: 2026-08-23

## 1. Purpose and implementation status

This contract defines the boundary between a business/edge service that owns the
match lifecycle and the GPU computer-vision service that owns anonymous visual
measurements. It supports 1–2 second independently decodable video segments so
analysis can start before a match ends.

This document and its JSON Schema define the wire contract. The repository has
stream endpoints and checkpointed cross-segment processors, including the
TrackNet source-frame adapter. This does not establish live-camera reliability,
model accuracy or the streaming SLO. The `/api/v1/jobs` complete-file API remains
separate.

Machine-readable assets:

- Schema: `docs/contracts/stream_session_v1/stream_session_contract_v1.schema.json`
- Valid examples: `docs/contracts/stream_session_v1/examples/`
- Example manifest: `docs/contracts/stream_session_v1/examples/manifest.json`
- Contract test: `tests/test_stream_session_contract.py`

## 2. Service boundary

The business/edge service owns:

- match start/end controls, users, `check_id`, registration and post-match claiming;
- camera/venue authorization, raw-video retention and durable business storage;
- segment creation, retry ledger and the opaque `client_reference`;
- team, score, ranking, victory/defeat and commercial rules.

The GPU service owns:

- temporary segment receipt and processing state;
- anonymous `track_id`, pose/person/shuttle observations and interaction candidates;
- confidence, evidence state, coverage and structured artifacts;
- model/runtime trace and session finalization.

The GPU service MUST NOT receive or emit a player name, user ID, `check_id`, team,
score, serve result, winner or ranking. `client_reference` is opaque: the GPU service
may store and return it for correlation but MUST NOT interpret it.

## 3. Common rules

### 3.1 Authentication and transport

- All endpoints except health checks require the same configured API credential as
  the existing GPU API (currently `X-API-Key`).
- Production transport MUST use HTTPS.
- The GPU container may listen on port 8080, but callers use a configured base URL;
  no public hostname or `localhost:8080` belongs in this contract.
- JSON bodies use UTF-8 and `application/json`.
- Segment upload uses `multipart/form-data`: one binary `segment` part plus one
  JSON `metadata` part conforming to `segmentMetadata`.

### 3.2 IDs and time

- `analysis_session_id` is generated by the GPU service and is stable for the
  complete visual-analysis session.
- `segment_index` starts at 0 and increments by 1 in source order.
- `source_start_time_sec` and every event `source_time_sec` use the source match
  timeline, starting at 0. They are never receipt wall-clock timestamps.
- `accepted_at`, `received_at`, `updated_at`, `emitted_at` and `sealed_at` are UTC
  RFC 3339 timestamps.
- `schema_version` is always `stream-session.v1` for this version.

### 3.3 Evidence integrity

Observation evidence is explicit:

| `evidence_state` | Meaning |
|---|---|
| `detected` | Direct model measurement at the source time. |
| `predicted` | Tracker/interpolation estimate; never counted as a direct detection. |
| `missing` | Expected evidence is absent; no position may be invented. |
| `derived` | Deterministic calculation from measurements. |
| `candidate` | Unconfirmed interpretation requiring confidence/review. |
| `finalized` | Session-level finalization fact, not a visual measurement. |

Low-confidence or absent evidence remains unknown. The service MUST NOT force a
player identity, shuttle position, contact, rally, shot type or score.

## 4. Endpoint contract

### 4.1 Create a session

`POST /api/v1/stream-sessions`

Request definition: `createSessionRequest`
Success definition: `createSessionResponse`
Success status: `202 Accepted`

The caller MUST provide `X-Idempotency-Key`. Repeating the same key and equivalent
request returns the original session (`200 OK`); reusing the key with different
content returns `409 invalid_state` and never creates a second session.

Required configuration:

- `analysis_mode`: v1 is fixed to `person_only`.
- `analysis_sample_hz`: `10`, `15` or `30`; default chosen by the caller, with 10Hz
  the production target.
- `pose_imgsz`: `640`, `960` or `1280`.
- `shuttle_detector`: `none`, `yolo` or explicitly enabled `tracknet_v3`.
- `generate_annotated_video`: production default is `false`.

Fixed-sport GPU deployments may additionally accept these optional anonymous
vision fields. They select visual constraints only; they never identify a
person, make a score decision or change the process to another sport.

- `sport_id`: an optional identity assertion. It must match the deployment's
  fixed profile (`badminton` or `tennis`).
- `session_mode`: required by the tennis deployment. It accepts only
  `singles_match` (two anonymous athletes) or `single_player_training` (one
  near-side anonymous athlete). The badminton compatibility deployment keeps
  `match` and its existing 2/4-person roster policy.
- `calibration_scope`: `full_court` or, only for tennis single-player training,
  `near_half_court`. In the latter case the four `court_corners` represent the
  near net-line corners followed by the near baseline corners, and map to the
  global near half of `tennis_singles_court_m_v1`.

The server derives `expected_player_count` and `max_roster_count` from a fixed
tennis mode: 2 for `singles_match`, 1 for `single_player_training`. A caller
cannot override those values. `shuttle_detector` is retained as a v1 wire-name:
the tennis deployment accepts `none` or `yolo`. `none` is pose-only. `yolo`
uses a configured `GOOD_TENNIS_STREAM_BALL_MODEL` when present, requiring the
exact class name `tennis_ball`. If absent, the explicitly packaged current
`yolo11s-ball.pt` may be used only as an experimental `badminton`-labelled
ball candidate; its event has `experimental=true` and never claims tennis
accuracy. If neither model is available, only a `yolo` request fails; the
pose-only service remains usable.

If `shuttle_detector=tracknet_v3`, `tracknet_overlap_frames` MUST be 7 when present,
because the temporal window length is 8. The built-in adapter reads every decoded
source frame independently of the 10/15/30Hz person sampling rate. Its checkpoint
retains the window across ordered segments when capture-side frame identity is
declared. Without it, the decoder estimates frame numbers from segment start
time and local FPS, and TrackNet treats the segment boundary as unknown rather
than asserting a continuous window.

### 4.2 Submit a segment

`POST /api/v1/stream-sessions/{analysis_session_id}/segments/{segment_index}`

Metadata definition: `segmentMetadata`
Success definition: `segmentReceiptResponse`

The path `segment_index`, metadata `segment_index`, content SHA-256 and actual byte
length MUST agree before a receipt is committed.

For a source that can declare a decoded frame sequence, the caller may send
`source_frame_start_index` and `source_frame_count` together. The GPU decoder
uses the declared starting index instead of estimating it from segment time and
local FPS, then checks that the decoded frame count matches. TrackNet may carry
its 8-frame window across a segment boundary only when both neighboring
segments declare source frame identity and their indices/timestamps are
continuous. Otherwise it marks ball continuity `unknown` and starts a new
window. A local file segmenter may declare its post-encode decoded sequence;
live capture should declare capture-side frame numbers. Neither proves that the
camera itself did not drop frames before numbering them.

| Case | HTTP | Required behavior |
|---|---:|---|
| First valid receipt | 202 | Persist bytes and receipt before responding; `reused=false`. |
| Same index, key, hash and length | 200 | Return the original receipt; `reused=true`; do not process twice. |
| Same index but different hash/length | 409 | `segment_hash_conflict`; retain the original receipt. |
| Later segment arrives first | 202 | Persist it with `waiting_for_predecessor`; do not process past the gap. |
| Session already sealed | 409 | `segment_after_seal`; never reopen implicitly. |
| Invalid metadata/content | 422 | `validation_error`; no durable receipt. |
| Temporary storage failure | 503 | `storage_unavailable`, `retryable=true`; no success receipt. |

The receipt confirms durable acceptance, not inference completion.

### 4.3 Query session status

`GET /api/v1/stream-sessions/{analysis_session_id}`

Response definition: `sessionStatusResponse`
Success status: `200 OK`

Status includes received/processed/**failed** segment counts, source-time progress,
remaining backlog, the next unfinished index, transport-missing indexes and
processing-failed indexes. `error` is reserved for a terminal session failure;
`processing_errors` records non-terminal per-segment failures. A caller can
therefore distinguish upload, queue wait, active analysis, recoverable evidence
gaps, drain and finalization.

When one accepted fragment fails to decode or run model/tracker inference, the GPU
service records its failure, starts a fresh continuity epoch for later fragments,
and continues. The result becomes `partial`; post-gap track IDs are namespaced and
MUST NOT be automatically linked to pre-gap identities. No missing position, ball
path or cross-gap movement is invented.

### 4.4 Read events

`GET /api/v1/stream-sessions/{analysis_session_id}/events?cursor={cursor}&limit={limit}`

Response definition: `eventsResponse`
Success status: `200 OK`

- Events are append-only and ordered by `(source_time_sec, event_id)` within a
  session.
- `next_cursor` is opaque and stable for replay. Re-reading the same cursor returns
  the same logical event range.
- An event ID is deterministic for one accepted segment/output so retrying a
  segment cannot create duplicate events.

Minimum event data:

| Event | Required `data` semantics |
|---|---|
| `person_observation` | Anonymous `track_id`, lifecycle state, measurement frame, bbox/court position/keypoints when evidence exists. |
| `shuttle_observation` | Anonymous shuttle track, image/court position when available, detector source and measurement quality. |
| `ball_observation` | Tennis raw image measurement, model label and detector quality. It is either dedicated `tennis_ball` evidence or explicitly experimental `badminton`-model evidence. A missing frame remains missing; this event does not assert a hit, rally, score or trajectory. |
| `interaction_candidate` | Candidate ID/type, related anonymous track IDs, evidence references and `review_required`; never forced fact. |
| `session_status` | State/stage transition and progress snapshot. |
| `session_finalized` | Final state, evidence gaps and artifact manifest. |

All five event types use the common `eventBase` schema. Tasks A/E may add fields
inside `data`; additions MUST be documented and backward compatible.

### 4.5 Seal and complete

`POST /api/v1/stream-sessions/{analysis_session_id}/complete`

Request definition: `completeSessionRequest`
Success definition: `completeSessionResponse`

- `expected_last_segment_index` freezes the caller's expected source range.
- With no gaps, the service seals input and returns `202` with `status=draining`,
  unless finalization already completed synchronously.
- With gaps and `allow_partial=false`, return `409 missing_segments`; leave the
  session open so the caller can upload missing pieces and retry completion.
- With gaps and `allow_partial=true`, seal input, preserve the missing indexes and
  finalize as `partial`. Missing regions MUST NOT be filled with invented evidence.
- A received fragment that fails GPU processing is a known processing gap. The
  service continues later fragments and ultimately finalizes as `partial` even if
  `allow_partial=false`; `failed_segment_indexes` and `processing_errors` make the
  degradation explicit.
- Repeating the identical complete request is idempotent and returns the current
  sealed/final state.

### 4.6 Cancel a session

`DELETE /api/v1/stream-sessions/{analysis_session_id}`

Success definition: `sessionStatusResponse`
Success status: `200 OK`

- Cancellation is cooperative: queued work stops immediately; running model/FFmpeg
  work receives a cancellation signal and the durable state becomes `cancelled`.
- The session record, receipts, progress and failure evidence remain queryable; this
  endpoint never deletes audit data.
- Repeating cancellation of a cancelled session returns the same terminal state.
- Cancelling `finalized`, `partial` or `failed` returns `409 invalid_state`.

## 5. State machine

```text
accepted -> queued -> running -> draining -> finalized
                         |           |
                         |           +-> partial
                         +-> interrupted_needs_rebuild
accepted/queued/running/draining -> failed | cancelled
```

Rules:

1. `accepted` means the session manifest is durable.
2. `queued` means work is waiting for GPU capacity or the first processable segment.
3. `running` means at least one segment is being or has been analyzed and more input
   may arrive.
4. `draining` means input is sealed and remaining backlog/final derivation is running.
5. `finalized` means the expected range is complete and final artifacts are durable.
6. `partial` means transport gaps were explicitly accepted or accepted bytes had
   known per-segment processing failures; exact indexes/errors remain queryable.
7. `interrupted_needs_rebuild` means cross-segment model/tracker continuity could not
   be safely restored. It is never silently converted into a new continuous track.
8. `failed` and `cancelled` are terminal. Retry requires a new session unless a
   future contract explicitly defines resume.

## 6. Anonymous track candidates

`track_candidates` exists so a business UI can offer post-match claiming before all
derived reports finish. It is not a user identity or a team assignment.

- `track_id` is the only persistent visual-person identity.
- Court zone/side is instantaneous spatial evidence and cannot change identity.
- Candidate states are `candidate`, `active`, `predicted`, `missing`, `closed` and
  `reassociation_uncertain`.
- Coverage and confidence must accompany candidates so fragmented tracks are not
  presented as reliable player profiles.

## 7. Errors

Every non-2xx response uses `errorResponse` and a stable `request_id`.

| Code | HTTP | Retryable by default | Meaning |
|---|---:|---:|---|
| `authentication_required` | 401 | No | Missing/invalid credential. |
| `session_not_found` | 404 | No | Unknown session ID. |
| `validation_error` | 422 | No | Invalid path, metadata or body. |
| `segment_hash_conflict` | 409 | No | Accepted index differs from submitted bytes. |
| `segment_after_seal` | 409 | No | Input is already sealed. |
| `missing_segments` | 409 | Yes | Completion is blocked until gaps are supplied or partial is explicit. |
| `invalid_state` | 409 | Contextual | Operation is invalid for the current state. |
| `storage_unavailable` | 503 | Yes | Receipt was not durably committed. |
| `engine_failed` | 500 | Contextual | Analysis engine failed; inspect details/status. |
| `interrupted_needs_rebuild` | 409 | No | Continuity cannot safely resume in this session. |

Per-segment `processing_errors` are returned in a successful status response, not
as an HTTP error response, because later fragments may still yield valid evidence.

Error messages are for operators; clients branch on `error.code`, never localized
message text.

## 8. Versioning and compatibility

- HTTP path remains `/api/v1/...`; payload schema version is independently frozen as
  `stream-session.v1`.
- Producers may add optional fields only when old consumers can ignore them.
- Required-field removal, meaning/unit changes, enum removal, state transition
  changes or endpoint semantic changes require `stream-session.v2`.
- Consumers MUST reject an unsupported major schema version rather than guessing.
- Existing `/api/v1/jobs` requests/responses and `detections.jsonl` readers are not
  changed by this contract.
